# Assessment 02: Model Context Protocol (MCP) & Tool Use — Giving Agents Hands

> Generated by lesson-validation (coverage mode) on 2026-07-01. Source spec: STUDY-PLAN.md entry for `04`.
> Deliberately diversified from quiz-01: probes schema *design*, when-*not*-to-use MCP, the init handshake, indirect prompt injection via tool results, roots, and cost levers — angles quiz-01 did not test.
> Currency of MCP transport + auth claims web-verified on this date against the 2025-11-25 spec (stdio + Streamable HTTP current; HTTP+SSE deprecated 2025-06-18; OAuth 2.1 for remote — all confirmed).

## Questions

1. You're writing a `scale_deployment` tool. Beyond "write a clear description," name the JSON-schema design choices that make the model call it correctly rather than mis-call it. _(tool schema design · augment)_
2. A teammate wants to wrap every internal REST endpoint as an MCP server "so agents can use them." When is MCP the *wrong* choice and you should just let deterministic code call the API directly? _(when-not-to-use · augment)_
3. Your read-only triage server returns pod logs to the model. How can a purely *read-only* server still be an attack vector? Name the mechanism and a mitigation. _(indirect injection · operate)_
4. Would you build one MCP server exposing k8s + cloud + CI, or three separate servers? Give the trade-off. _(server composition · operate)_
5. What happens in the MCP `initialize` handshake, and why does capability/version negotiation matter for forward- and backward-compatibility? _(handshake · operate)_
6. Beyond a least-privilege credential, how do you make a `delete_namespace` tool safe to expose to an agent at all? _(mutation gating · operate)_
7. Every tool definition *and* every tool result consumes context tokens on every turn. What are the two cost levers, and how do they conflict with capability? _(context cost · operate)_
8. MCP "prompts" surface as slash commands. How do they differ from a tool, and who triggers them? _(primitives · augment)_
9. You need an audit trail of everything an agent did via your MCP server for compliance. Where do you instrument it, and what do you capture? _(observability · operate)_
10. An agent picking its own tools is more flexible than a fixed script. State the governance cost of that autonomy and one way to bound it. _(determinism vs flexibility · operate)_
11. Sketch the minimal components of an MCP server that exposes `kubectl get/describe` to an agent — process, transport, credential, tool defs. _(server sketch · operate)_
12. What is the MCP "roots" capability and what problem does it solve? _(primitives/currency · operate)_
13. stdio (local subprocess) vs remote Streamable HTTP — when do you reach for each on a platform team? _(transport choice · operate)_

## Answer key

1. Good schema design: **required vs optional** fields (so the model knows what it must supply); **`enum`/pattern constraints** on values (e.g. `replicas` bounded, `namespace` from an allow-list) so the model can't emit an invalid value; **per-parameter `description`s** (each field is itself a mini-prompt); **narrow types** and **granularity** (one focused tool beats an overloaded one with a `mode` flag). — **Partial**: §1.1 shows per-field descriptions + `required` and states the description is "effectively a prompt," and §4.1 shows the SDK generating a schema from the signature/docstring — but the lesson never enumerates *design* levers such as `enum`/constraint use or tool granularity to steer correct calls.
2. MCP earns its keep when a **non-deterministic agent must discover and choose** among capabilities at runtime. If the caller is your own deterministic code that already knows which endpoint to hit, wrapping it in MCP adds a protocol hop, a tool-catalogue token cost, and a model round-trip for no benefit — call the API directly. MCP is for agent-facing surfaces, not service-to-service glue. — **Missing**: the lesson is uniformly pro-MCP; §8 flags ecosystem maturity but never the "just call the API" boundary or the determinism-vs-agent framing for when to skip MCP.
3. A read-only server can carry an **indirect prompt-injection** payload: attacker-controlled text sitting *in the data it returns* (a pod log line, an event message, a PR title) re-enters the model's context as a `tool_result` and can carry instructions the model then acts on. Mitigation: treat tool results as **untrusted input** — output sanitisation/redaction in middleware, and the credential/guardrail layer so an injected instruction still can't reach a mutating tool. — **Partial**: §7.1 has output sanitisation (redact secrets/PII before results re-enter context) and §6.2 flags prompt injection as targeting the access seam — but the lesson never states that a read-only server's *returned data* is itself the injection channel.
4. Separate servers give **independent blast radius, credentials, and lifecycle** per system (the k8s server holds only the cluster token; a compromised cloud server can't touch the cluster) and match MCP's one-server-per-system model. One mega-server is simpler to register but concentrates credentials and widens the tool catalogue. A **guardrail gateway** gets the best of both: separate backends behind one governed entry point. — **Partial**: §3.1 defaults to a server per system and §7.2 unions them behind a gateway with the catalogue-cost nuance — but the explicit "merge vs split" credential-isolation trade-off is never posed as a build decision.
5. On connect, client and server exchange an `initialize` request/response that negotiates the **protocol version** and each side's **declared capabilities** (does the server offer tools? resources? prompts? sampling?), so each speaks only what the other supports and old/new peers interoperate without breaking. — **Missing**: §5 covers *tool discovery* (`list_tools` at startup) but never the `initialize` handshake or version/capability negotiation.
6. Beyond scoping the token so it *could* delete only when intended: a **human-confirmation gate** (`ask` before execution) and a **server-side policy gate** in middleware — e.g. require an approved change ticket, else the guardrail raises `ToolError` and never forwards the call — plus **audit** of the attempt. Defence in depth: even a permitted call is refused by policy. — **Covered**: §6.2 (confirmation gate) + §7.3 (change-ticket policy gate, `ToolError`, audit).
7. Lever one: the **tool catalogue** — every tool's name/description/schema is sent on every request, so more tools = more budget spent *and* worse tool selection. Lever two: **tool-result verbosity** — each returned payload re-enters context and accumulates over a multi-call loop. Both conflict with capability: more/broader tools and richer results make the agent more capable but cost budget and dilute accuracy. — **Partial**: the catalogue lever is covered well (§7.2 Nuance + §8 "Catalogue breadth vs context") but the *result*-token lever is never named as a cost knob (§7.1 mentions results re-enter context only for redaction, not budget).
8. A **prompt** is a reusable message template the **server author** pre-writes and the **user** triggers via the host (a slash command); it *seeds* the conversation. A **tool** is invoked by the **model** mid-reasoning and *acts*. The model never auto-calls a prompt. — **Covered**: §3.2 + the capability table.
9. Instrument at the **middleware/guardrail-gateway chokepoint** (`on_call_tool`), which sees every call before it reaches a backend. Capture the **actor, tool name, arguments, and outcome (allowed/denied)** — one audit log for every attempt, allowed or not. — **Covered**: §7.3 (`audit_log.write(actor, call, args)`, "every attempt is logged") + §7.2 ("one audit log of every action").
10. Cost: an agent that chooses its own steps has a **wider, less predictable blast radius** — it can call any exposed tool, including in an order you didn't foresee, so what it *can* break is bounded only by its access, not by a script. Bound it at the **access layer**: least-privilege credentials + a guardrail gateway that enforces policy and audits, so autonomy stays inside a hard boundary regardless of what the model decides. — **Covered**: §6 (credential boundary) + §7 (guardrail policy/audit) + §8 "Capability vs. blast radius"; the substance is present though the determinism-vs-flexibility pair isn't named as such.
11. **Process**: a small server (e.g. Python SDK) wrapping your existing k8s client. **Transport**: stdio for a local per-user tool, or Streamable HTTP for a shared governed one. **Credential**: a scoped read-only ClusterRole token (`get`/`list` on pods/events) the server runs as. **Tool defs**: `get_pod_status`/`describe_*` handlers whose signature+docstring become the JSON schema. — **Covered**: §4.1 (SDK wrapper) + §3.4 (transports) + §6.1 (scoped ClusterRole) + §1.1 (schema).
12. **Roots** let the *host/client* tell the server which URI/filesystem boundaries it is allowed to operate within (e.g. "only these workspace directories"), scoping a server's view of the environment and preventing it from wandering outside sanctioned locations. — **Missing**: the lesson covers tools, resources, prompts, and sampling but never roots.
13. **stdio** for local, per-user, isolated tools — simple, no network surface, but unmanaged (every user runs their own copy). **Streamable HTTP** for a shared server the platform team runs centrally — governable, observable, auditable, but it's a network service you must scale, secure, and add caller auth (OAuth 2.1) to. Control vs. operational burden. — **Covered**: §3.4 + §8 "Local (stdio) vs. remote (HTTP) transport."
