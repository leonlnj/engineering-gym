## Questions

1. What does a model's "parameter count" (e.g. 8B vs 70B) physically refer to, and what is the capability-vs-cost trade-off in reaching for the bigger one?  _(model size · operate/augment)_
2. Why is the first token of a response slow while later tokens stream out faster, and why do output tokens cost more than input tokens?  _(prefill vs decode · operate)_
3. The embedding table inside the LLM and a standalone embedding model (the kind you call in a RAG pipeline) — same thing or not?  _(confusable terms · augment/operate)_
4. Your team wraps a model behind an existing REST endpoint that CI already calls. Name three assumptions baked into "it's just an API call" that an LLM breaks.  _(integration · augment)_
5. Why do chat UIs stream tokens one at a time, and what does streaming *not* change about compute or cost?  _(streaming · operate)_
6. What do `max_tokens` and stop sequences control, and why does `max_tokens` matter for latency/cost budgeting even when the model would stop on its own?  _(control knobs · operate)_
7. "It only predicts the next token." How does next-token prediction produce output that looks like reasoning or planning?  _(core computation · why)_
8. Multiple users hit one model server at once. How does batching serve them, and what is the latency-vs-throughput trade-off for any single request?  _(batching · operate)_
9. Why can the same sentence cost more tokens in another language, or as source code, than as plain English prose?  _(tokenization cost · operate)_
10. Structurally, how does the model distinguish a system prompt from a user message — is there a hard, enforced boundary?  _(roles/boundary · augment)_

12. A KV-cache grows as the conversation grows. Why does that put a hard ceiling on concurrent users and max context on a given GPU?  _(KV-cache sizing · operate)_

## Answer key

1. Parameters are the model's **learned weights** — the billions of numbers (embedding rows, attention projections, output matrix) adjusted during training; "8B" means ~8 billion of them, and count roughly tracks capacity. The trade-off is the GUIDELINES pair **capability vs. cost**: a bigger model is generally smarter but costs more per token and needs more/bigger GPUs (more memory, slower per token). — **Partial**: the *physical* meaning is covered (§ intro "billions of numeric weights"; §2.3 "learned parameters — just numbers"), but the **capability-vs-cost** trade-off of model *size* is never named — §8 Practical Limits omits it. Borderline scope (model selection leans toward lessons 08/11), but it is a GUIDELINES trade-off pair the lesson could name in one §8 bullet.
2. The prompt is consumed in a single forward pass over all input tokens (**prefill**) — that up-front pass is what makes the *first* token slow on a long prompt — then each output token is its own sequential forward pass (**decode**), so a 500-token answer is ~500 passes. Output costs more than input because each output token triggers a full pass, whereas the whole input is processed once in parallel. — **Partial**: the mechanics are all present (§4.1 "runs the full token sequence through all the attention layers once"; "A 500-token answer is 500 forward passes"; §7 "latency scales with output length"), but the lesson never names **prefill vs decode** as the two phases nor states the input-cheaper-than-output cost asymmetry explicitly. Deeper TTFT/throughput tuning is lesson 08.
3. **Not the same.** The internal embedding table has one row *per token* and is looked up by ID (§2.1); a standalone embedding model in RAG produces *one vector per chunk/sentence* of text and is a separate model you call. Both live in "meaning-as-geometry" space and both are compared by cosine, which is why they're easy to fuse. — **Missing**: §2.2 says the embed-and-cosine operation "is the basis of vector search and RAG" but never disambiguates the per-token table from a document/sentence embedding model. Largely lesson-06 territory, but a one-line contrast here would pre-empt a common conflation.
4. Any three of: (a) **non-deterministic / non-cacheable** — same input can return different output, so you can't `assertEqual` or cache it; (b) **latency is variable and scales with output length**, not fixed; (c) **it can hallucinate** — a confident, well-formed wrong answer that looks identical to a right one; (d) cost is per-token and unbounded unless capped; (e) **knowledge cutoff** — it's blind to anything new/private. — **Covered**: §8 Practical Limits (probabilistic/non-cacheable, cost, cutoff, fluency-vs-truth) + §4.2 Nuance. The augment-thread "behind a REST endpoint" framing isn't explicit, but every property needed to answer is present.
5. Streaming works precisely because generation is **already token-by-token** (§4.1) — the server can emit each token the instant it's sampled instead of waiting for the whole response, cutting *perceived* latency. It does **not** change total compute, total tokens, cost, or the fact that the full answer still takes N sequential forward passes. — **Partial**: the underlying mechanism (one token per pass, appended and looped) is fully covered, so streaming is inferable, but the lesson never names token streaming or its cost-neutrality. Minor / inferable.
6. `max_tokens` caps the response length (an upper bound on decode passes); **stop sequences** are strings that, when generated, end the response early. `max_tokens` matters for budgeting because it bounds worst-case output — hence worst-case latency and cost — and because the response reservation must fit inside the context window (§5.1's "reserved for the response"). — **Partial**: the length-cap / end-of-sequence concept is covered (§4.1 "emits a special end-of-sequence token or hits a length cap"; §5.1 reserved-response line), but the explicit `max_tokens` and `stop` *parameters* and their budgeting role aren't spelled out. Low importance; API-surface detail leans toward lesson 02.
7. Because the training corpus is so vast, the statistically most-likely continuation of well-structured text *is* a coherent, on-topic one — so pattern-completion, run in a loop, produces text that reads like reasoning or planning even though no goal, plan, or belief is tracked between steps. — **Covered**: §3.3 (failover walkthrough → "completing a pattern, not following a plan"; "no goal, plan, or fact being tracked between steps") + § intro + §9. A core, strongly-taught theme.
8. A server groups concurrent requests into a **batch** and runs them through the GPU together (modern servers use *continuous* batching, slotting new requests in as others finish), which raises tokens/sec **throughput** by amortising the GPU over many requests — at the cost of a little added **latency** for any single request that waits to be batched. — **Missing**: batching appears only as a *source of non-determinism* (§4.2 Nuance) and the KV-cache Note says GPU memory "caps how many requests a GPU can serve," but continuous batching and the per-request latency-vs-throughput trade-off are explicitly lesson-08 scope. Correctly deferred; not a lesson-1 defect.
9. BPE gives common (mostly English) strings single tokens and splits rare strings into more pieces (§1.1). Other languages and source code appear less in training / use characters that fragment into more sub-word pieces, so the *same meaning* takes more tokens — and you pay per token. — **Partial**: the mechanism (frequent → one token, rare → split; "any string is representable as some sequence of known pieces") is fully explained and "token counts are model-specific" is noted (§1.1–§1.2), but the specific consequence for non-English/code cost is never called out.
10. Structurally there is **no hard, enforced boundary** — system and user text are concatenated into the *same* token stream and flow through the same attention; the "system" role is a convention (special delimiter tokens + training) the model is trained to weight more, not a protected channel. This is exactly why prompt injection works. — **Missing**: the lesson lists "system prompt + instructions" only as a budget line item (§5.1) and never explains system vs user roles or the absence of a real boundary. Correctly deferred to lessons 02 (prompt engineering) and 11 (security/prompt injection).
11. Generally **no** — meaning is *distributed* across the whole vector, not stored one-concept-per-axis; individual dimensions rarely correspond to a clean human-readable feature. The geometry (relative positions/directions) carries meaning, not any single coordinate. — **Partial**: §2.3 establishes meaning is an "emergent byproduct, never designed in" ("no one wrote a rule that latency is near throughput"), from which a careful reader infers dimensions aren't individually labelled, but the per-dimension-interpretability point isn't stated outright. Low importance.
12. The KV-cache holds every prior token's keys/values in **GPU memory** and grows linearly with tokens (§5.2), so each concurrent request consumes a slice of finite VRAM; the more/longer the requests, the fewer fit — bounding both concurrency and max usable context on that GPU. — **Partial**: the lesson establishes the cache lives in GPU memory and grows with tokens, and *points* at the ceiling ("how the cache caps how many requests a GPU can serve") but explicitly defers the sizing math to lesson 08. Correctly deferred; concept is seeded here.
