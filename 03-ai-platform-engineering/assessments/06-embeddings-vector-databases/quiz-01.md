## Answer key

1. Vectors from different embedding models live in different, incompatible coordinate spaces, so comparing them is meaningless; changing models later means re-embedding the whole corpus. — **Covered**: §1.2 Note.
2. The embedding model maps meaning to geometric proximity, so semantically similar texts land near each other even with no shared words; keyword search matches tokens, so it misses vocabulary mismatches. — **Covered**: §1.2.
3. cos = dot product / (product of magnitudes), ranging 1 → 0 → −1; direction captures "about the same thing" independent of text length/intensity. — **Covered**: §2.1. *(Note: the worked `cos(A,B)` example was arithmetically wrong as found — see Resolved.)*
4. Brute-force k-NN compares the query to every stored vector: 10M vectors × 1,024 dims ≈ 10B floating-point ops per query — too slow for a tens-of-ms request and too CPU-hungry to serve many users. — **Covered**: §3.1.
5. Exactness for speed: give up guaranteed-exact neighbours for *approximate* ones found by skipping most comparisons. — **Covered**: §3.2.
6. HNSW = layered proximity graph, very high recall + low latency, but full graph in RAM and slow builds — best latency-critical. IVF = clustered cells probed nearest-first, lighter memory and faster builds, recall depends on cells probed — best huge/memory-constrained corpora. — **Covered**: §4.1/§4.2 + table.
7. Build-time: HNSW `M`/`ef_construction`, IVF `lists` — fixed at build, changing them means rebuilding. Search-time: HNSW `efSearch`, IVF `nprobe` — set per query to tune each search. Conflating them is a common error. — **Covered**: §4.2 Nuance.
8. IVF runs k-means over a sample to learn centroids (`lists` of them) and assigns each vector to its nearest cell; if the distribution drifts (new tenant/doc type) the centroids no longer fit and the index must be rebuilt to stay balanced. — **Covered**: §4.2.
9. Raise `efSearch`/`nprobe` to examine more of the graph/more cells → higher recall but more time per query; there's no setting that maximises both, so tune to the accuracy the downstream LLM actually needs. — **Covered**: §4.3.
10. The filter must run *inside* the search so the index never returns another tenant's vector; getting it wrong is a data leak, not just a relevance miss. — **Covered**: §5.1.
11. `pgvector` for up to a few hundred thousand vectors with modest QPS — one fewer system, transactional consistency. A dedicated DB earns its cost at tens of millions of vectors, high throughput, or tight latency. Start with what you operate. — **Covered**: §5.2.
12. Dot product and Euclidean (L2). The choice ties to normalisation: on length-normalised vectors cosine and dot product rank identically (dot is cheaper); L2 matters when absolute magnitude is meaningful — follow the embedding model's recommendation. — **Partial** (as found): only cosine was presented; alternatives/selection were absent.
13. Pure vector search misses exact lexical matches — specific error codes, UUIDs, rare flags, negation — because it matches meaning, not tokens. The fix is **hybrid search**: run a dense (vector) and a sparse (keyword/BM25) query and merge the results. — **Missing** (as found): the lesson sold semantic over keyword but never noted the reverse blind spot or hybrid retrieval.
14. **Quantization** — store vectors compressed: scalar (8-bit, ~4× smaller, small recall hit) or product quantization / IVF-PQ (8–16× smaller, larger recall hit). ~200 GB of raw floats becomes ~50 GB scalar-quantized — fits on one machine. Cost: some recall. — **Missing** (as found): the lesson flagged HNSW's RAM cost but never named quantization.
