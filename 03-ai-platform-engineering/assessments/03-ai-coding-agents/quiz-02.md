## Questions
1. You need to generate a new Terraform module (or Helm chart) for a standard service. Why is this a good fit for a coding agent, and what single practice most improves the result? _(fit for IaC generation · augment)_
2. A colleague calls a coding agent "just fancy autocomplete on a loop." What is the one architectural feature that makes it categorically different, and what does that feature depend on to work? _(defining feature · augment)_
3. Frame the determinism-vs-flexibility trade-off for choosing between a hand-written script and an agent for a platform task. Give one task that belongs on each side. _(script vs agent · augment/operate)_
4. You drop an agent into a 2M-line monorepo and it makes an incoherent change. Explain the mechanism behind the failure and two mitigations. _(large-repo failure · augment)_
5. What is the role of a `CLAUDE.md` / project-instructions file, and why does it materially change agent output quality on *repeated* tasks? _(project memory · augment)_
6. Compare interactive agent use with wiring the same agent unattended into CI. Why does the same tool flip from asset to hazard? _(interactive vs unattended · operate)_
7. Your agent's context window is filling up mid-task on a long refactor. Name the harness mechanisms that extend effective working memory, and the trade-off each one carries. _(context-window management · augment)_
8. Agents shift the engineer's work from writing to reviewing. Why can review burden become the new bottleneck, and how does task scoping reduce it? _(review burden · augment)_
9. Beyond token cost, why is an agentic loop slow in wall-clock terms, and why is that latency acceptable interactively but disqualifying for some ops automations? _(latency · operate)_
10. Claude Code, Cursor, and Copilot agent mode differ in harness design. Name one meaningful axis of difference and why it matters for platform work. _(tool landscape · augment)_
11. For an agent that can touch a cluster, describe how you would bound its blast radius using more than just command permissions. _(blast radius · operate)_
12. Why is plan-before-act mode valuable specifically on ambiguous or large changes, and what class of error does it catch that verification-after (tests) cannot? _(plan mode · augment)_
13. Give a concrete platform task where an agent reliably breaks down despite looking capable, and explain the root cause. _(where it breaks · augment)_

## Answer key
1. Good fit because it is context-heavy boilerplate/toil: the agent reads the existing repo patterns and produces a coherent first pass, exactly the "context-heavy toil (Helm charts, Terraform migrations)" the lesson names as the sweet spot. The single practice that helps most is **scoping the task tightly** (a concrete, verifiable goal) plus supplying conventions the agent cannot infer via `CLAUDE.md`. — **Covered**: §6.1 (Scope, Context, Review) + §6.2.
2. The **observe/feedback step**: the harness executes a real tool and feeds the result back into context, so each step is conditioned on ground truth rather than a fixed guess. It depends on the agent actually having tool access to run the build/test/read the real error — without that, it "reasons in the dark and will guess." — **Covered**: §1.1 loop + §3.2 Note (ground truth) + §4.
3. A hand-written **script is deterministic** — same behaviour every run — and is right for a *known, repeatable* job (a fixed deploy sequence). An **agent is flexible** — it picks its own steps — and is right when the path is *unknown up front* (diagnosing a novel CrashLoopBackOff), at the cost of being harder to bound and predict. Reach for the agent where the task varies, not where a script already suffices. — **Partial** (as found): §1.2 non-determinism and §7 "Autonomy vs. control" cover *bounding* the agent, but the determinism-vs-flexibility pair (when to pick a script *instead of* an agent) was never named, despite being a GUIDELINES trade-off pair flagged "to name explicitly."
4. Mechanism: the repo far exceeds the context window, so the agent works from a **partial view** and misses a caller/config/convention living in a file it never opened — "it does not know what it did not read." Mitigations: break the task into smaller, verifiable units; scope tightly and supply pointers/conventions (`CLAUDE.md`); (and prompt caching/decomposition to keep each unit inside the window). — **Covered**: §5.2 + §5.1 + §6.1.
5. It is auto-loaded into the context of *every* session, so conventions/constraints the agent cannot infer are always present without re-typing — the durable, repo-level equivalent of a system prompt. Every future task inherits the convention instead of relearning or guessing it. — **Covered**: §6.1 (`CLAUDE.md` snippet + explanation).
6. Non-determinism plus compounding early misreads are tolerable when a human reviews each result; unattended there is no review to catch a wrong path or a non-reproducible fix, so the same behaviour becomes a hazard and needs heavy guardrails (bridge to lesson 05). — **Covered**: §5.2 + §7 (Interactive vs. automated) + §8.
7. **Context compaction** — replace older turns with an LLM summary to free room; trade-off: lossy, can drop a detail the agent later needs. **Subagents** — run a self-contained sub-task in an isolated context and return only the result; trade-off: the subagent works blind to the parent's context. Plus **task decomposition** to keep each unit inside the window. — **Partial** (as found): only decomposition was offered (§5.1/§6.1); compaction and subagents — the actual harness features for extending working memory in effective use — were absent.
8. If the agent produces a large, sprawling diff, review time can exceed the time saved, and skipping review converts the time-saver into a liability. Scoping the task to a small, verifiable change keeps the diff reviewable and gives a clear pass/fail (tests) to anchor the review. — **Covered**: §6.1 (review like a PR) + §6.2 + §7 (Speed vs. review burden).
9. A multi-step task is many *sequential* model round-trips, so wall-clock time runs to minutes, not the sub-second of one call. Acceptable interactively (a human is waiting to review), but disqualifying for anything on a tight latency budget — another reason agentic ops belongs behind async, human-paced workflows. — **Partial** (as found): token *cost* was covered thoroughly (§2.2, quadratic), but the distinct *latency* dimension was not named in §7.
10. Axis: **terminal-native, broad shell/file access** (Claude Code) vs **IDE-embedded with tighter UI integration** (Cursor, Copilot agent mode). It matters for platform work because platform tasks are shell/`kubectl`/CI-heavy, so a terminal-native agent fits ops workflows more naturally than an editor-bound one. — **Covered**: §3.2 (final paragraph); platform-relevance left implicit.
11. Beyond the `allow`/`ask`/`deny` command list: run the agent under a **scoped, least-privilege credential** (read-only cluster RBAC, not admin `kubeconfig`) and in a **sandboxed workspace** (git worktree or throwaway container) so stray writes land on a copy. Together these cap blast radius from three directions — what it can run, what its credentials permit, and where its writes land. — **Partial** (as found): plan mode, step budget, and emit-diff-not-apply were covered, but scoped credentials/RBAC and sandbox isolation were not (some legitimately deferred to lessons 04/11).
12. Plan mode surfaces a misunderstanding of *intent/approach* before any edits — it catches the "solved the wrong problem" class of error cheaply. Verification-after (tests) only catches wrong *implementation* of whatever goal the agent pursued; a test can pass on the wrong task. — **Covered**: §3.2 (catch misunderstanding before editing fifteen files).
13. Wiring up a novel *internal* system / private API the model never saw in training: it hallucinates plausible-but-wrong calls, flags, or Helm values because plausible code is what it generates and it has no ground truth for internal/fast-moving APIs. (Also: a large-monorepo change where the relevant caller lives in an unopened file; or a long-horizon epic where an early misread compounds.) — **Covered**: §5.1 (hallucinated internal APIs, long horizons) + §5.2 (context limits).
