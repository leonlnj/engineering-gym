## Questions

1. A platform team is deciding between Basic and Enhanced for a workload that will never use virtual nodes, but is projected to scale past a few hundred worker nodes within a year. Why might they lean Enhanced anyway? _(tier selection / node ceiling · exam-ready)_
2. A Basic cluster created two years ago is still on Flannel overlay networking. The team now wants Enhanced for the SLA. What blocks them, and what's the only way to unblock it? _(upgrade path constraint · exam-ready)_
3. Why can't a virtual node run a DaemonSet — explain the actual mechanism, not just "it's not supported." _(virtual node restriction mechanism · production-reasoning)_
4. On a managed node, setting `limits.cpu` above `requests.cpu` lets a pod burst into spare capacity. What happens if you try the same on a virtual node, and why? _(resource allocation model · exam-ready)_
5. `kubectl exec` and `kubectl logs -f` are both unavailable on a virtual node. How would you actually diagnose a pod that's crash-looping there? _(virtual node troubleshooting · production-reasoning)_
6. A cluster runs entirely on a virtual-node pool and traffic triples. Does the Cluster Autoscaler add capacity to handle it? Explain. _(scaling mechanism / virtual node exception · production-reasoning)_
7. You run `oci ce cluster update --kubernetes-version v1.32.1` against a cluster whose node pools are all on an older version. Are the pods on those nodes affected immediately? What governs how long that gap is tolerable? _(two upgrade surfaces / skew policy · exam-ready)_
8. Contrast an in-place and an out-of-place node pool upgrade on the one axis that matters most to a team that wants a rollback path. _(upgrade strategy selection · production-reasoning)_
9. Why does OSOK need its own dedicated IAM credential rather than using whatever identity the cluster's control plane already runs as? _(OSOK auth model · production-reasoning)_
10. The lesson says the public/private endpoint choice is "made at cluster creation." What CLI flag or parameter on `oci ce cluster create` actually sets it? _(endpoint choice mechanism · exam-ready)_
11. Virtual nodes bill per pod at exactly the declared request. Is that necessarily cheaper than an equivalent managed-node pool sized to the same aggregate load? What would you need to know to answer that? _(virtual node cost model · production-reasoning)_
12. A colleague new to OCI says "OKE is just managed Kubernetes, so Oracle runs everything." What's the one-sentence correction, and what's the one artifact that's true regardless of tier or node-type choice? _(OKE-specific vs. generic managed k8s · exam-ready)_

## Answer key

1. Enhanced raises the worker-node ceiling well above Basic's; if projected node count could approach or exceed Basic's ceiling, Enhanced is needed independent of any virtual-node need. — **Covered**: §2.1 table ("Worker node ceiling: Lower / Higher, increasable on request") and §7.
2. Basic→Enhanced upgrade requires VCN-Native pod networking; a Basic cluster still on Flannel has no upgrade path at all and must be recreated. — **Covered**: §2.2.
3. DaemonSets exist to run one pod per node; a virtual node isn't a persistent machine with a stable identity to schedule "one per" against — it's a per-pod execution slot conjured on demand, so there's no fixed node set to enumerate one-per. — **Covered**: §3.3 ("DaemonSets have nothing to run one-per-node on").
4. The pod is rejected — requests must equal limits exactly, because there's no shared node headroom to borrow against; Oracle provisions precisely what's requested, per pod. — **Covered**: §3.2 and its Nuance.
5. Not addressed. — **Missing**: §3.3 states exec/logs -f/SSH are all unavailable but never answers the immediate follow-up — what replaces them (e.g. non-follow `kubectl logs`, `kubectl describe`/Events, an OCI Logging integration). A reader is left with a debugging dead end.
6. No — there is no Cluster Autoscaler on virtual nodes at all; each new pod provisions its own execution slot the moment it's scheduled, so there's no "add a node" decision to make. — **Covered**: §3.3, §5.3, and the closing line of §5.4.
7. No immediate effect — a control-plane upgrade touches no worker node. The skew policy bounds the drift: node pools must run the same or an earlier compatible version, and from Kubernetes 1.28 onward the control plane may run up to three minor versions ahead before the pool must catch up. — **Covered**: §5.1.
8. In-place replaces nodes inside the same pool, so once nodes are replaced there is no old pool left to fall back to; out-of-place builds a new pool alongside the old one and only removes the old pool once the new one is proven, preserving a rollback path throughout. — **Covered**: §5.2.
9. OSOK acts on the OCI API on your behalf to provision resources outside the cluster; a dedicated, service-scoped IAM user limited to the resource types it manages bounds its blast radius and keeps it from silently breaking if one engineer's personal access changes. — **Covered**: §6.3 (explicitly mirrors Module 02's `ocirsecret` principle).
10. Not shown. — **Partial**: §4.1 explains the concept and its consequence for `kubectl` clearly, but no snippet in the lesson demonstrates the actual creation-time parameter that sets endpoint visibility — the one `cluster create` example (§2.2) shows tier and networking mode, not endpoint choice.
11. Not addressed. — **Missing**: §3.2 establishes that virtual nodes are billed/provisioned per pod, and §3.5 calls "no node sizing" an operational win, but the lesson never quantifies or compares this against equivalent managed-node capacity — a reader can't actually reason about the price trade-off, only the qualitative one.
12. Oracle's management guarantee is scoped to the control plane only — every data-plane choice (tier, node type, upgrade strategy) stays yours; the one constant regardless of choice is that Oracle always runs the control plane (API server, etcd, scheduler) as an IAM-governed OCI resource. — **Covered**: §1.1, §1.2 Nuance, §8 Summary.
