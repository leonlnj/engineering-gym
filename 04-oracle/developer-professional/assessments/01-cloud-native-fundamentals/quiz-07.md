## Questions

1. A Vault secret referenced by `vaultVariables` is rotated while a build run is in flight. Which value does the running build use, and when does the new one take effect? _(secret lifecycle · production-reasoning)_
2. A build step commits a generated file back to the same repository that triggered it. What goes wrong, and what stops it? _(trigger loop · production-reasoning)_
3. Someone `kubectl apply`s a hotfix directly into the green (standby) namespace while blue is live. What happens to that change on the next blue-green deployment? _(out-of-band drift · production-reasoning)_
4. Define "rollback" precisely for each strategy: rolling, blue-green, canary. _(rollback semantics · exam-ready)_
5. Beyond cost, what *security* property do fresh-per-run build runners give you? _(runner isolation · production-reasoning)_
6. Two pushes land on `main` seconds apart and two build runs execute concurrently, both exporting `IMAGE_TAG`. Do they collide? _(concurrency · production-reasoning)_
7. A canary shift to 10% shows elevated errors. What do you do, and what did those 10% of users experience — i.e., what does canary *not* protect? _(canary honesty · production-reasoning)_
8. A `build_spec.yaml` step sets `IMAGE_TAG` but the author forgot to list it under `exportedVariables`. What breaks downstream and why? _(export contract · exam-ready)_
9. A developer keeps 4.9 GB of artifacts in the Cloud Shell home directory. What starts failing, and what's the remedy? _(Cloud Shell pressure · exam-ready)_
10. Why can't you make the fresh-runner download tax disappear by caching "on the runner"? Where must the cache live instead? _(cache architecture · production-reasoning)_

## Answer key

1. The run keeps the value resolved when it started; the rotated value applies from the next run. — **Partial**: §4.3 says resolution happens at run time, but per-run resolution semantics (in-flight behavior, when rotation lands) are unstated.
2. Each build's commit re-triggers a build: an infinite loop billing forever. Stopped by exclude file filters on the generated path (or not committing from builds). — **Covered**: §4.6 exclude filters make this direct.
3. The next deploy applies the pipeline's manifests into the standby namespace, overwriting the out-of-band change — the pipeline owns those namespaces, and manual edits there are lost by design. — **Partial**: §4.5 covers namespace mechanics but never addresses out-of-band drift and its overwrite-on-deploy consequence.
4. Rolling: redeploy the previous version (roll forward to old tag). Blue-green: switch traffic back to the still-running previous environment. Canary: shift the subset's traffic back to the stable version. — **Covered**: §4.5 table states all three.
5. Isolation: no state from one build can leak into the next — a compromised or poisoned build can't contaminate later runs via the runner. — **Partial**: §4.3 gives freshness and cost but not the security-isolation benefit.
6. No — each run has its own variable scope, and hash-based tags mean the two runs produce distinctly-tagged images (`tag = commit hash`). — **Covered**: §4.3 + §5.2 make both halves explicit enough to answer.
7. Shift traffic back to stable; those users experienced real errors — canary *limits* blast radius, it does not eliminate it; the price is stated as two live versions serving users. — **Covered**: §4.5 table (trade-off column).
8. Downstream stages and the deployment pipeline see no `IMAGE_TAG`; placeholder substitution produces an empty/unresolved reference — the export list is the contract, setting a variable is not enough. — **Covered**: §4.3 presents declaration as the hand-off contract (failure mode inferable and consistent).
9. New writes and builds in the session start failing on space; remedy is cleanup (or moving artifacts to proper storage) — the 5 GB is fixed. — **Covered**: §6.2 + Practical Limits.
10. The runner is destroyed after the run, so any on-runner cache dies with it; the cache must live in a service that survives — pre-baked images in OCIR, registry-backed layer caches. — **Partial**: cost is stated in §4.3, but the where-must-the-cache-live reasoning and mitigations are absent (same gap as quiz-05 Q5).
