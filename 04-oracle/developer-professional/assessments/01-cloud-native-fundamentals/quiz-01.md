1. Adopting microservices forces a team to also invest in containers and CI/CD — why? What does each solve that the architecture created? _(pillars interlock · production-reasoning)_

3. Two services read and write the same database table. What eventually breaks, and which design rule does this violate? _(microservice design methodology · production-reasoning)_
4. An app on OKE loses user sessions whenever a pod is rescheduled. Which twelve-factor factors are violated, and what is the fix? _(12-factor applied · production-reasoning)_

7. In `build_spec.yaml`, how do you (a) consume a secret without writing it in the file, and (b) hand a value computed during the build (like an image tag) to the deployment pipeline? _(build spec mechanics · exam-ready)_
8. A release needs instant, total rollback capability and the budget tolerates brief double capacity. Which deployment strategy, and what exactly is the cost? _(strategy selection · exam-ready)_
9. Can you use a canary strategy when deploying to OCI Functions? _(strategy constraints · exam-ready)_

## Answer key

1. Microservices multiply the number of deployable units, so packaging must be uniform (containers) and releasing must be automated (CI/CD) — hand-releasing thirty services doesn't scale. — **Covered**: §1.1 states the pillars as a dependency chain.
2. Advise a well-structured monolith; microservices trade code complexity for operational complexity (network failure modes, deployment infrastructure) a 4-person team can't absorb. — **Covered**: §2.1 names when microservices lose.
3. Schema changes now require coordinated releases — the shared table re-couples the services into a hidden monolith. Violates database-per-service. — **Covered**: §2.2, shared-database anti-pattern with the release-train consequence.
4. Factors VI (stateless processes) and IX (disposability): session state lives in pod memory. Fix: move session state to a backing store so any replica serves any request. — **Covered**: §3.2 uses this exact failure shape.
5. Factor V. The build pipeline produces the immutable image (build); the deployment pipeline releases and runs it — the stages live in different resources by construction. — **Covered**: §3.1 table row V and §4's pipeline split.
6. A Notifications (ONS) topic (required at creation) and a dynamic group + IAM policies for the pipelines' resource principals. Missing policies typically surface as 404 "not found", not 403. — **Covered**: §4.1 including the 404 nuance.
7. (a) `vaultVariables` — the spec holds a Vault secret OCID, resolved at run time; (b) `exportedVariables` — declare the name, set it in a step, later stages and the deployment pipeline reference it. — **Covered**: §4.3, both mechanisms explained.
8. Blue-green: deploy to standby, validate, switch all traffic; rollback is switching back. Cost: full double capacity while both environments run. — **Covered**: §4.5 table + theatre analogy.
9. No — blue-green and canary are gated to OKE and instance-group targets; Functions releases rolling-style. — **Covered**: §4.5 and Practical Limits call the Functions pairing a trap.
10. Code Editor: in-console, nothing to install, Cloud Shell tools available. Constraints: small fixed home directory, inactivity/session timeouts — a scratch editor, not an IDE. — **Covered**: §6.1–6.2 + Practical Limits figures.
11. Push events (branch-filterable) via triggers; external GitHub repos attach through a connection resource backed by a personal access token stored in OCI Vault. — **Partial**: §4.2/§4.6 cover push + connections, but the lesson names only push — whether pull-request events can also trigger builds is unstated (and unverified; flagged in the summary).
