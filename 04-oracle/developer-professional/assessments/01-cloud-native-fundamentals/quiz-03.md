## Answer key

1. Missing IAM policy for the pipeline's dynamic group — OCI surfaces unauthorized access as 404 "not found" because it hides resources the caller cannot see. Check policies before OCIDs. — **Covered**: §4.1 nuance teaches exactly this instinct.
2. The deliver/artifact mapping: an artifact registered with a fixed tag (or a delivery stage mapped to the wrong artifact) instead of a `${...}`-substituted one. — **Covered**: §4.4 names this as the classic cause.
3. Factor XII — run admin tasks from the same image/environment as the app. In the flow: as a step or job in the pipeline using the built image, not from a laptop. — **Partial**: §3.1 row XII covers the factor and same-image rule; the lesson does not show where such a task sits in a DevOps pipeline (no stage-level guidance).
4. Buys: no runner fleet to patch/scale, no state leaking between builds. Costs: cold caches — every run re-pulls dependencies and rebuilds layers, so build times include that tax every time. — **Partial**: §4.3 states the fresh-VM benefit; the recurring cold-cache cost is not mentioned.
5. An OKE cluster, a Functions application, or a compute instance group. — **Covered**: §4.5.
6. Two triggers (or two pipelines): one with a feature-branch filter starting build-only, one filtered to `main` whose build hands off to the deployment pipeline. — **Covered**: §4.6 branch-filtered triggers + §4.4/§4.5 build→deploy chaining make the wiring direct.
7. Carve by business capability/bounded context — pick a capability with clean seams, give it its own data store, route callers through its API. — **Partial**: §2.2 teaches the decomposition rules, but says nothing about *incremental* migration (choosing the first service, strangler-style coexistence with the monolith).
8. Because the app must be self-contained (factor VII): it exposes a port, and the platform's Services route to it — the platform discovers the app, the app doesn't embed platform specifics. — **Covered**: §3.1 row VII (thin but sufficient for the exam-ready question).
9. Canary — deploy with no traffic, validate, shift a subset. You accept a slower rollout and two versions serving users simultaneously. — **Covered**: §4.5 table.
10. The Cloud Shell home directory persists between sessions; loss risk: the ~6-month non-use purge (with 60 days' notice). — **Covered**: §6.2 + Practical Limits figures.
11. Not answered by the lesson: instance groups are named as a deployment target but never defined (what they are, rolling across VMs, when plain VMs beat OKE). — **Missing**: §4.5 names the target; no definition or selection guidance anywhere.
12. It forces every project to have an eventing/alerting channel from day one — pipeline outcomes (failures, waiting approvals) are observable by default instead of silently vanishing. — **Covered**: §4.1 + walkthrough step 8 give the rationale.
